# オーナー一人と AI 協働者一体で回す、適応的・反復的な開発プロセス

## 1. はじめに

ある小規模プロダクトを、人間のオーナー一人と、AI コーディング協働者
一体という体制で、段階的に育てているところです。寿命としては中長期
で継続的に育てる前提を置いていますが、現時点ではまだ v1 にも達しておらず、
運用の歴史も浅いというのが実情です。その短い運用のなかで自然と固まって
きた進め方を、プロダクト固有の語彙を外して書き起こしたのが本稿です。
実証されたベストプラクティスというよりは、現時点での到達点を整理した
スナップショットだと思って読んでいただければと思います。

ただし、抽象化しているとはいえ、元になっている実例には偏りがあります。
対象はエンドユーザー向けの業務アプリケーションではなく、開発者向けの
UI フレームワークです。そのため本稿の関心は、ユーザー行動や業務価値
の検証よりも、公開インターフェース、アーキテクチャ、設計判断の履歴、
長期的な拡張余地にやや強く寄っています。この偏りは、後で Spec Kit や
仮説階層モデルと比較するときの前提になります。

進め方の系譜としては、Martin Fowler が予測的計画 (predictive planning)
と対比して論じる **適応的計画 (adaptive planning)** と **反復的
(iterative)** 開発の系列に属します。フェーズごとに「これは正しい設計
か?」「この計画は本当に目的に沿うか?」を問い直し、答えが変われば計画
ごと書き換える、という仮説検証の反復を主軸に据えています。事前にすべて
を設計しきって走り抜けるのではなく、走りながら設計し直していきます。

ただしこの「走りながら直す」を、口頭やコードの揮発した記憶に頼らず、
**文書として明示的に積み重ねる** ことが本稿の特徴です。新しいフェーズ
に入るときはまず文書を書き、合意が取れてからコードに触れます。実装中
に文書に書いていない判断が必要になったら、コードを止めて文書を直し
ます。こうして検証の経過と合意の履歴を文書側に残し、後から「なぜこの
設計にしたのか」「いつ何を捨てたのか」を遡れる状態を保ちます。

文書合意の動機はそれだけではありません。より重く効いているのは、
**オーナーの意図を一塊ではなく粒度ごとに保つ** ことの方かもしれません。
オーナーがプロダクトに対して持っている意図は、ひとつの均質な塊では
なく、目的・受入基準・構造・個別の設計判断という異なる粒度に分かれて
存在しているはずのものです。ところが明示的な合意点を置かなければ、AI
協働者は手元で判断できることを片端から自分で決めて先に進み、その小さ
な判断の積み重ねが、本来オーナーが粒度を分けて決めるべきだった事柄を
勝手に塗りつぶしていきます。フェーズ内の局所的な選択が構造上の決定と
して振る舞いはじめ、実装レベルの取り回しがいつのまにかプロダクトの
『そういうものだ』 — 後追いで成立した、暗黙の規定 — として固まって
いきます。本稿の進め方は、これらの粒度を文書として別々に持ち、それぞれ
を別々の合意点で固めることで、低い粒度の判断が勝手に高い粒度の合意を
書き換えてしまわないようにするものです。後から遡れることと並んで、
これが文書合意のもう一本の柱です。

ここまでで、業界の標準語彙となった仕様駆動開発 (spec-driven
development、以下 SDD と書きます) や、GitHub が公開した Spec Kit と
の関係を気にする読者が多いと思います。本稿の進め方は SDD の系譜にも
一部重なります。ただし「仕様」という言葉が指す対象が両者で異なって
おり、その差は本稿の構成のかなめになります。とくに本稿の元になった
対象が UI フレームワークであるため、素朴に「仕様」と聞いて想起される
もの (アーキテクチャや公開インターフェースの記述) が、通常のアプリ
ケーション開発よりも前面に出ます。この整理は第 6 章 (本稿における
仕様の定義) と第 11 章 (Spec Kit との比較) で正面から扱いますので、
それまでは「仕様」という語の周辺は判断を保留して読み進めていただければ
と思います。

加えて、本稿の進め方は **オーナー一人 + AI 協働者一体** という極端に
小さい体制を前提にしています。並列に複数のエージェントを走らせたり、
複数の人間レビュアーを挟むことは、いまのところ行っていません。この
体制前提が運用全体の細部を決めているので、第 2 章でその含意を整理して
おきます。

本稿は手順書というよりも、なぜそれを採用するのかという設計上の動機と、
向いていない場面の検討、そして他の流派との比較を含む読み物として書いて
います。手順そのものはプロダクトごとに調整する前提で、原則と判断軸を
中心に据えました。

**この章のまとめ**: 本稿が記述するのは、適応的・反復的に仮説検証を回す
開発プロセスです。検証の経過と合意を文書として積み重ねる方式は、後追い
の遡及だけでなく、オーナーの意図を粒度ごとに保ち、AI 協働者の手元の
判断や実装上の選択が勝手に高い粒度の合意を規定してしまうのを防ぐ装置
でもあります。「オーナー一人 + AI 協働者一体」という体制前提も最初に明示
します。SDD や Spec Kit との関係、本稿が言う「仕様」の定義は後の章で
扱います。

## 2. この文書の前提となる体制

本稿の進め方は、次の体制を前提に組み立てています。これが変わると、適用
できる範囲が大きく変わるので、最初に独立した章として明示しておきます。

- **オーナーは人間が一人**。プロダクトの目的に対する最終的な意思決定
  権限はこの一人に集中しています。
- **協働者は AI コーディングエージェントが一体**。複数体を並列で走らせる
  運用は採用していません。
- **進行は基本的に逐次**。会話を一本の流れとして進め、合意の取り直しも
  そのうえで行います。

この体制が運用に与える影響は、想像より大きいです。

第一に、**合意の単位を「明示的なやり取り一回」に揃えられます**。レビュ
アーが複数いれば全員の同意を取る手続きが必要になり、合意の境目はもっと
粗くなります。オーナー一人なら、ひとつの文書に対する「了承」が決定の
単位になり、判定が遅延しません。逆に言えば、この体制を増員すると、
本稿の合意モデルはそのままでは成立しません。

第二に、**AI 側のセッションが切れるたびに記憶が失われる** ことを前提
に組まれています。人間同士の協働なら「先週相談したあれ」で通じる部分
が、AI 協働者では文書に書かれていなければ無いに等しいです。だから本稿
は「あとで書く」を許しません。書かなければ次回には消えてしまうから
です。

第三に、**並列のエージェントが存在しないので、ブランチ運用が単純で
よい**ことになります。複数体を並列に走らせるなら、ブランチ分離と統合
のルールはもっと重くなります。本稿の運用が比較的軽いブランチ管理で
済んでいるのは、並列性を放棄しているからにほかなりません。

第四に、**オーナーの認知負荷が単一の人格に集中しています**。レビュー、
意思決定、優先順位付け、振り返りの判定、すべてが同一人物に乗ります。
後述の確認項目は、この一人の判断ぶれを抑えるための装置でもあります。

体制を拡張する方向 (人間レビュアーを加える、エージェントを並列化する)
については、本稿の射程の外にあります。少なくとも合意モデル・記憶モデル・
ブランチモデルのいずれもが、再設計を要します。

なお、プロダクトが v1 に近づいた段階では、対外的な提案受付の仕組み
として RFC ベースの合意形成への移行を構想しています。これは「オーナー
が最終決定者」という現在のモデルを否定するものではなく、外部からの
提案を受ける窓口として上に積む層を想定しています。とはいえ現状はそこ
に至っておらず、本稿が記述するのは v1 以前の小体制での運用にとどまり
ます。

**この章のまとめ**: 本稿はオーナー一人 + AI 協働者一体・逐次進行という
体制を前提にしています。合意の単位、記憶の前提、ブランチの単純さ、認知
負荷の集中という四つの面で、運用全体がこの前提に依存しています。

## 3. 設計判断を文書に固定するという原則

ソフトウェア開発において、「あとでドキュメントを書く」は多くの場合
「書かれない」と同義になります。実装が先に存在してしまうと、文書は
「コードの説明書」になり、設計の選択肢や捨てたものの記録は失われます。

本プロセスでは順序を反転させます。フェーズに入る前に、少なくとも次の
三点を文書に書きます。

- そのフェーズが満たすべき受入基準
- 検討した設計案と、得られるもの・失うもの
- 採用案と、その一行根拠

書き終えたものをオーナーがレビューし、明示的に合意してから着手します。
ここで重要なのは、合意の対象がコードではなく文書そのものである、という
点です。コードはあとで変えられますが、「なぜそうしたか」は後追いでは
復元できません。だから記録すべきものを記録する側を先に置きます。

この順序を守ると、副次的な効果として、議論の発散を抑える力が働きます。
文書化されていない案は、レビューの対象になりません。レビューに乗せる
には書かなければなりません。書かれた選択肢の中から選ぶ、というルール
が、口頭で出てきた思いつきが暗黙のうちに採用されてしまう事故を防いで
くれます。

**この章のまとめ**: 設計の選択肢と採用根拠を、コードを書く前に文書と
して固定します。文書を合意の対象に据えることで、後から復元できない
情報が失われるのを防ぎます。

## 4. 仮説と制約を切り分ける

このプロセスでもっとも効いているルールは、**フェーズに入る前に書かれ
たタスクの並びは「制約」ではなく「仮説」として扱う**、というものです。

たとえばマイルストーン計画を立てる段階で「フェーズ 3 では機能 X を実装
する」と書いたとします。フェーズ 2 が終わった時点でフェーズ 3 の事前
文書を書くとき、誘惑として「機能 X をどう実装するか」をいきなり考え
がちですが、そこで一段戻ります。**この機能 X は、フェーズ 3 の受入基準
を満たす最短経路なのか?** と問い直します。受入基準は手段ではなく目的
の側の言葉で書かれているはずで、目的に対して別の経路が存在する可能性
は常にあります。

実際このプロセスを運用していると、事前文書の作成中に「当初のタスク列
は目的と手段を取り違えていた」と気づくことが定期的に起こります。そこ
で計画文書のタスク列を書き換え、必要なら受入基準のほうを直します
(後者は目的仕様に手を入れる重い変更で、ビジョン DR と呼ぶ上位の判断
記録を起こすことになります。詳細は後の章で触れます)。これは計画への
裏切りではなく、計画が仮説であったことの正当な帰結です。

逆に、合意された設計判断 (DR に書かれた採用案) は仮説ではありません。
これは **履歴ごと固定します**。後から覆すときは元のエントリを書き換
えず、新しいエントリを追加して「以前の判断はこれに置き換えられた」と
リンクします。判断の変遷そのものが、将来の議論にとっての一次情報に
なります。

この「仮説の側」と「制約の側」を意識して切り分けることで、計画は柔軟
に保ちつつ、決定は不変に保てます。両者をどちらか片方に倒すと、計画
が硬直するか、決定が水のように流れて記憶できなくなるかのどちらかに
崩れます。

**この章のまとめ**: 着手前のタスク列は仮説、合意済みの設計判断は制約
です。仮説は事前文書のたびに洗い直し、制約は新規エントリで上書きし
ながらも履歴を消しません。

## 5. 文書の役割分担と単一正本

文書を合意の単位にすると、自然と文書の種類が増えます。種類が増える
と、今度は **どこに何があるか分からなくなる** という別の問題が顔を
出します。これに対する答えは「カテゴリごとに役割を一つに絞り、情報の
正本をひとつだけに置く」ということです。

おおまかな分担は次のようになります。

- **目的とロードマップ**: プロダクトが何のために存在し、どこへ向かう
  か。受入基準の正本もここに置きます。
- **マイルストーン計画**: 中粒度の合意。フェーズ分割、依存関係、受入
  基準との対応、対象外スコープを書きます。個別の設計判断は書きません。
- **判断記録 (DR)**: 検討した案・採用案・棄却した案を残す、決定の不変
  な記録です。本稿では二段にわけて運用しており、フェーズ内の設計判断
  を記録する **フェーズ DR** (一般的にいう ADR と同等) と、目的・受入
  基準そのものの改訂を記録する **ビジョン DR** があります。両者は同じ
  書式と規律 (案の網羅、二軸のリスク、上書きルール) に従い、対象とする
  ものだけが違います。なお ADR は本来 architecture decision record の略
  で字義どおりにはアーキテクチャ限定の用語ですが、実務上は判断記録
  一般を指す略称として広く使われています。本稿はその慣行をさらに進めて、
  ビジョンレベルまで含めた総称として「判断記録 (DR)」を採用します。
  以下、二段の区別が必要な箇所では「ビジョン DR」「フェーズ DR」と
  書きわけ、両方に共通する話では単に「DR」と書きます。
- **進捗ノート**: 可変のタスク列、step 単位の作業ログ、引き継ぎメモ。
  実装中の現在地を置くための一時的な作業面で、フェーズ終了時に削除
  されることを前提に書きます。
- **探索的メモ**: まだ固まっていない仮説、開いている問い、横断的な
  スケッチ。確定したら判断記録に吸収して元は削除します。
- **参照資料**: 複数の文書から繰り返し引用される、抽出済みの安定資料。
  作業中のものは置きません。
- **変更履歴**: マイルストーン完了時に、外向けに残す記録。

第 6 章以降で使う **作業計画** という語は、このうちマイルストーン計画
と進捗ノートをまたぐ総称です。マイルストーン計画は、フェーズ分割や
依存関係のような中粒度の合意を持ちます。進捗ノートは、その下で実装中
の step とタスク列を持ちます。前者は合意されたら固定寄りに扱い、後者は
実装中に動く仮説として扱います。同じ「計画」でも、保存される重みが
違います。

判断に迷ったときは「これは合意済か、計画か、揺れているか、引用される
素材か、今日の作業ログか」と自分に聞きます。混ざりはじめたら必ず分離
します。

このうち、**進捗ノートと探索的メモは基本的に削除する** という運用を
徹底している点が、外から見て独特な部分かもしれません。残すと「これは
まだ生きているのか?」という疑問が読者の側に発生し、結果として文書群
全体の信頼性が下がるからです。フェーズに閉じた細かい作業仮説が、外部
に公開すべき合意の粒度と混ざってしまうことも避けたいです。git の履歴
に残っていれば十分で、今日のディスクに置いておく必要はありません。

**この章のまとめ**: 文書カテゴリは役割を一つに絞り、情報の正本をひとつ
だけに置きます。役目を終えたものは削除を既定にします。

## 6. このプロセスにおける「仕様」とは何か

ここまで何度も「仕様文書」「仕様優先」と書いてきました。これだけ繰り
返す以上、本プロセスにおいて「仕様」が何を指しているかを正面から定義
しておくほうがよいでしょう。とくに後で SDD と比較する場面では、両者
の「仕様」が同じ言葉のもとで違う対象を指していることを意識しておか
ないと、議論が噛み合いません。

結論から書くと、本稿では「仕様」という言葉を、まず **何を満たすべき
か** と **どんな構造で満たすか** の二層に分けて考えます。前者を目的
仕様、後者を構造仕様と呼ぶことにします。一般にソフトウェア開発で
「仕様」と呼ばれるものは、この二つのどちらか、または両方を指すことが
多いはずです。

- **目的仕様**: プロダクトが何のために存在し、どこへ向かうか、どんな
  受入基準を満たせば「進んだ」と言えるか。目的とロードマップがこれに
  対応します。受入基準を含むため、これは一般的な意味でも仕様にかなり
  近い層です。
- **構造仕様**: 全体のアーキテクチャと、外向きに公開するインターフェース。
  版を切って固定し、改訂は明示的な合意経由で行います。実装はこの層に
  従います。

この二層に対して、別種の文書が二つ重なります。ひとつは **作業計画**
です。これは仕様そのものというより、目的仕様と構造仕様をどの順序で
実装へ落としていくかを示す計画です。マイルストーン計画のフェーズ分割
や依存関係と、進捗ノート上の step / タスク列がここにあたります。前者は
中粒度の合意、後者は実装中の可変な作業仮説です。

もうひとつは **判断記録 (DR)** です。これは目的仕様・構造仕様・作業
計画と同列の「対象」ではありません。むしろ、それらが確定される前に
置かれる由来の記録です。目的仕様を変える前にはビジョン DR があり、
構造仕様を決める前にはフェーズ DR やアーキテクチャ上の判断があり、
作業計画を立てる前にも pre-doc 的な検討があります。DR は「何が仕様か」
そのものというより、「なぜその仕様や計画になったか」を、検討した案ごと
残す台帳です。

本プロセスの文書群の中心にあるのは、目的仕様と構造仕様です。その下流
に作業計画があります。そして各対象の上流に判断記録があります。運用上
はこれらをまとめて参照するため、広い意味で「仕様」と呼ぶことがありますが、
厳密には目的仕様・構造仕様・作業計画・判断記録は同じ種類のものでは
ありません。

この分け方で重要なのは、それぞれが **異なる更新規律** を持つことです。
目的仕様は動かす頻度を低く設計します。構造仕様は合意点ごとに版が切られます。
作業計画は、マイルストーン計画の合意済み部分と、進捗ノート上の可変な
step / タスク列に分かれます。前者は合意後に制約として扱われ、後者は
実装中も動く仮説として扱われます。判断記録は累積し、覆すときも履歴を
消しません。同じ文書体系に含まれていても、変更の重みも手順も違う、
という点が本プロセスの設計のかなめになっています。

構造仕様は、現状ではフェーズ着手前の事前文書作成の過程で書き起こされ、
合意が取れた時点でその版が固定される、というスナップショット的な扱い
になっています。継続的に書き直されるライブ文書というよりは、合意点
ごとに版を切る形に近いです。実装はその版に従って進めます。目的仕様は
その構造仕様が何のために存在するかを与え、作業計画はどの順序でそこへ
到達するかを示し、判断記録はなぜその形を選んだかを残します。

この設計から、いくつかの帰結が生まれます。

**第一に、仕様はそれ自体では「実行可能」ではありません**。再生成して
動かす対象ではないし、コードを自動生成する種でもありません。仕様は
「いま何が決まっていて、いつ決まったか」を人間と AI が共有するための、
合意の所在を示す台帳です。実装は別の労働として実行されます。

**第二に、仕様だけでなく判断記録が累積します**。目的仕様や構造仕様の
最新版は一つですが、古い判断は新しい判断で置き換えられても、台帳上には
両方残ります。これは文書体系全体を「最新の意図の鏡」としてだけ扱う流派
とは逆向きの設計であり、過去にどの選択肢を見送ったかを後から遡れること
を優先しています。

**第三に、仕様は AI への単独の指示書ではありません**。AI 協働者が参照
する重要な入力ではありますが、それを読み込めばそのままコードに変換
できる、という位置づけにはしていません。あくまで人間と AI の **対話の
累積結果** であり、AI はその更新と参照の両方に関与します。仕様の更新
自体が会話と合意の所産です。

以上を批判的に検討すると、この設計には明らかな代償があります。

- **文書数が多く、地図が必要になります**。新しく入ってくる人 (新しい
  AI セッションを含む) は、まず文書間の関係を理解しないと正本にたどり着けま
  せん。単一仕様書を読めば全体が分かる、という単純さは捨てています。
- **同期事故が起きます**。同じ事実が文書をまたいで言及されているとき、
  片方だけ更新されて不整合になる事故が定期的に起きます。これは正本を
  ひとつに絞る規律 (前章) でかなり防げますが、ゼロにはなりません。
- **更新の判断コストが恒常的にかかります**。何かを変えたいとき「これ
  は目的仕様の変更か、構造仕様の変更か、作業計画の変更か、判断記録の
  追加か」を毎回判断する必要があります。混同すると履歴が壊れます。

これらの代償を支払ってでも文書を分ける理由は、二本あります。

一本は、**文書体系の各部分が異なる速度で古びる** ことを吸収するため
です。目的仕様はプロダクトの寿命のあいだ安定させることを意図し、構造
仕様は合意点ごとに版を切ります。作業計画のうち、マイルストーン計画の
合意済み部分は固定寄りに扱い、進捗ノート上の step / タスク列はフェーズ
進行と同期して書き換わります。
同じ合意文書群に含まれていても、各部分が想定する時間スケールは桁違いに
異なります。これを単一文書に詰め込むと、書き換えの圧力が必ず文書全体
にかかり、結果として「目的すら頻繁に書き換わる」か「作業計画を書き換え
にくい」かのどちらかに崩れます。文書を分けることでこの圧力差を吸収
しています。

もう一本は、第 1 章で触れた **オーナーの意図を粒度ごとに別々の合意点
で固める** ためです。対象ごとに別の文書として存在するからこそ、低い
粒度の変更 (実装上の選択や、フェーズ内の局所的な決定) をいじっただけで
高い粒度の合意 (目的・受入基準・構造) が動いてしまわないようにできます。
仮にすべてを一本の文書に書いていたら、低い粒度の更新と高い粒度の更新が
同じ文書編集として扱われ、両者の区別が運用上消えてしまいます。AI
協働者が低い粒度で下した判断が、文書編集の副作用としていつのまにか
高い粒度の合意を書き換えていた、という事故も起こりえます。対象を
別文書に分けることは、この事故を構造的に防ぐ装置でもあります。判断
記録を各対象の上流に置くのも同じ
理由で、合意済みの目的仕様・構造仕様・作業計画と、それらを生んだ検討
過程を混ぜないためです。

ここまでで言及していないもう一つの側面に触れておきます。本稿の文書体系
は、人間と AI の合意記録であると同時に、**将来の外部読み手に向けた記録**
でもあります。新たに参加する寄稿者、プロダクトの利用者、後任の AI
セッション。DR が棄却された案まで残し、構造仕様が外向けの文書品質
を保とうとするのは、内部の記憶補助だけが理由ではなく、この後発の
読み手を念頭に置いているからでもあります。

ただし正直に書くと、現時点でこの外部読み手はまだ実在しません。実際
に読んでいるのはオーナー本人と AI 協働者の二者だけで、外部読み手の
存在はあくまで設計上の想定にとどまります。それでもこの想定を保つこと
で、DR の棄却理由の網羅や、文書の言語規約 (共有文書は共通言語で書く、
など) といった規律が「内輪の便宜」に倒れず維持されます。外部読み手
を想定することは、内部の規律を緩めないための装置として機能している、
と言ってよいと思います。前章で触れた v1 接近時の RFC 運用への移行は、
この想定上の読み手を実在に変える節目になります。

**この章のまとめ**: 本稿で一般的な「仕様」に近いのは、受入基準を含む
目的仕様と、アーキテクチャや公開インターフェースを定める構造仕様です。
作業計画はそれらを実装へ落とす計画であり、Spec Kit で言えば plan や
tasks に近い領域です。ただし、plan に近いマイルストーン計画と、tasks
に近い進捗ノート上の step / タスク列では保存の重みが違います。判断記録
はさらに別で、目的仕様・構造仕様・作業計画の上流に置かれ、それらが
なぜ採用されたかを累積的に残します。代償
として文書数と判断コストが増えますが、時間スケールの違うものを混ぜず、
オーナーの意図を粒度ごとに別々の合意点で固定するための、意図的な設計
です。

## 7. 合意・実装・検証のループ

ここまでの原則を、フェーズ単位の実際のループに落とすと、次のような
五段になります。

1. **事前文書**: 受入基準を読み直し、検討した案を列挙し、採用案を
   選び、一行根拠を添えます。
2. **合意**: オーナーが文書をレビューし、明示的に承認します。承認が
   取れるまではコードに触りません。
3. **実装**: 文書に書かれた範囲のなかで作業します。範囲外に出る波及
   を発見したら、その場で止めて報告し、文書を直してから再開します。
4. **振り返り**: マージの前に、確認項目に沿って作業を振り返ります
   (第 9 章)。
5. **マージ**: 振り返りに通り、合意が取れたものだけが取り込まれます。

このループを「重い」と感じるかは、プロダクトの寿命と、設計判断の密度
に依存します。短命なスクリプトや、判断が単純な実装作業に対しては、
明らかに過剰な仕掛けです。一方で、複数年にまたがって育てるプロダクト
や、設計上の選択が後々まで影響するレイヤ (アーキテクチャ、公開 API、
データ構造) に対しては、このループの厚みが情報の散逸を防いでくれ
ます。

本稿の元になった UI フレームワークでは、まさにこの後者の比重が大きい
です。公開 API、DSL、ABI、描画モデルのような公開面は、一度利用者に
依存されると軽く動かせません。だからフェーズごとに事前文書を書き、
合意を取り、実装後に振り返ってから取り込むというループを、あえて
厚めにしています。重いのは文書を書くこと自体が目的だからではなく、
利用者が長期に依存する面を安定させるためです。

なお、実装中に **セッションごとの作業範囲は計画の最上位 1 項目** だけ
に絞る、という運用も併用しています。これは「合意の単位を小さく保つ」
ことの延長で、合意が空気のように曖昧になるのを防ぐためのものです。
セッションのはじめに「いまの作業範囲はこの項目です」と宣言してから
始めると、途中で別の問題に目移りしても戻ってこれます。

この最上位 1 項目が、実装中の **step** にあたります。step のタスク列や
検証ログは判断記録には入れず、進捗ノートに置きます。step は作業を進める
ための仮説であり、ビルド失敗、直接確認、実装中の発見によって分割・
並べ替え・削除されることがあります。だからこそ、判断記録のように長期
保存される文書とは分け、フェーズが閉じたら必要な情報だけを判断記録や
変更履歴に蒸留して、進捗ノート自体は消す運用にしています。

**この章のまとめ**: フェーズは事前文書・合意・実装・振り返り・マージ
の 5 段で進めます。セッション単位の作業範囲も最上位 1 項目に絞り、
それを step として進捗ノート側で扱います。合意の単位を小さく保ちつつ、
可変の作業ログを長期保存される判断記録から分離します。

## 8. マージは段階的な合意点である

ブランチをどう切るかという話には深入りしません。本プロセスにおいて
ブランチは「合意の境界を git で表現したもの」にすぎず、運用の本質は
別のところにあります。

押さえておきたいのは一点だけで、**マージ先によってマージ前に必要な
振り返りの基準が変わる**、という事実です。

- 作業をひとつのフェーズ枠に取り込むときは、軽めの振り返りでよいです。
  ここはまだフェーズの内側で、外から見える挙動は変わっていません。
- フェーズの成果を主系列 (main 等) に取り込むときは、重い振り返りに
  なります。ここで受入基準が本当に満たされているかを確認し、ロード
  マップや変更履歴との整合を取り、ユーザに見える挙動の最終確認を行い
  ます。
- 主系列に取り込むことと、外に公開すること (公開リポジトリへの反映、
  配布) は、さらに別の合意点として扱います。取り込み判断と公開判断
  は、必ずしも同じタイミングで下す必要がないからです。

ようするに、**「軽い合意」と「重い合意」と「外向け公開」の三段** が
あり、それぞれに別の判定基準と別の承認が必要、という整理です。これ
を区別せずに一気通貫で進めると、外向け公開のときに必要な確認が省略
されたり、軽く済ませてよい振り返りが過剰に重くなったりします。

**この章のまとめ**: マージ先によって必要な振り返りの基準と承認は
変わります。軽い合意・重い合意・外向け公開を別の段に分けて扱います。

---

## 9. 振り返りはマージ前に置く

振り返りというと、事後の反省会を思い浮かべる読者が多いと思います。
本プロセスでの振り返りは少し違っていて、**マージという行為の直前に
置かれた確認項目** です。事後ではなく、未然のための仕掛けです。

具体的には、マージ前に次のような項目を「あり / なし」(あるいは「成功
/ 失敗」「必要 / 不要」) で答えます。

- 共有仕様文書に変更があったか
- ビルドとテストは綺麗に通っているか
- 計画書や DR を見直す必要が出ているか
- 計画外の「ついで」の変更が混ざっていないか
- 後続のフェーズに技術的負債を持ち越していないか
- 主系列へのマージなら、受入基準が本当に満たされているか
- 主系列へのマージなら、ユーザに見える挙動の確認は済んでいるか

「あり」「失敗」「必要」が一つでもあれば、オーナーに報告して承認を
取り直します。**確認項目を通過すること自体はマージの許可ではない**、
とあらかじめ宣言してあるのが効いていて、機械的な了承で先に進む誘惑を
構造的に潰せます。

逆に、すべてが「なし」で、ローカルの自動確認も通っていて、作業範囲も
フェーズ枠内に収まっている場合に限り、軽めのマージは報告と同時に実行
してよい、という **ファストトラック** (条件付きの軽量経路) を許しています。
重い合意 (主系列へのマージ) のほうにファストトラックはありません。

**この章のまとめ**: 振り返りは事後の反省ではなく、マージ前の確認項目
として運用します。通過は許可ではなく、報告と承認の起点にします。

## 10. 判断記録の書き方

DR は本プロセスでもっとも長持ちする文書で、ここに書き残すものの質
がプロセス全体の品質を決めると言ってよいです。以下に挙げる書き方の
要点は、フェーズ DR とビジョン DR の両方に共通して適用されます。両者
は対象とするものが違うだけで、文書としての規律は同じです。

書き方の要点は四つあります。

**第一に、検討した案をすべて残します**。実際には三案検討したのに、
最終 DR には二択しか書かない、という現象がよく起きます。読み手から
見ると一見綺麗ですが、棄却された案の根拠が消えるので、後から同じ案
を再提案する人を止められません。棄却された案は一、二行でかまわない
ので、検索の足場として残します。

**第二に、リスクを二軸で書きます**。フェーズ内で実装が回るかどうか
という「収束する不確実性」と、将来の拡張で再訪が必要になるかどうか
という「収束しない予測」は、まったく別の種類の話です。これを単一の
リスク語彙にまとめると、確度の異なる主張が同じ強度に見えてしまいます。
本プロセスではラベル自体を別にして、両者を取り違えないようにしてい
ます。

**第三に、覆すときは履歴を消しません**。後のフェーズで以前の判断を
否定することは普通に起こります。そのとき元のエントリを書き換える
のではなく、新規エントリを追加し、元のエントリには「これは新しい
判断で置き換えられた」というリンクを足すだけにします。判断の変遷は
将来の議論にとって貴重な一次情報です。

**第四に、DR にタスクの並びを書きません**。DR は不変の決定記録、
タスク列は作業計画のうち可変な部分です。両者を同じ文書に同居させると、決定が
タスク列に引きずられて改変されたり、逆にタスク列が決定の重みを帯びて
柔軟性を失ったりします。タスク列は進捗ノート側に置きます。

**この章のまとめ**: DR は「検討した案の網羅・二軸のリスク・履歴を
消さない更新・タスク列を含まない」の四点を守ります。長期保存される
文書としての品質を保つための、最小限の規律です。

## 11. Spec Kit (SDD) との比較

GitHub の Spec Kit が示した SDD のフロー — 仕様策定 (specify)、計画
(plan)、タスク化 (tasks)、実装 (implement) の四段、それぞれを専用の
スラッシュコマンドで起動し、AI が成果物 (spec.md、plan.md、tasks.md)
を生成する — は、いまや AI コーディングの標準的な参照点になっていま
す。本稿の進め方も同じ「仕様優先」の系譜に属していますが、いくつか
の軸で立場が異なります。読者は Spec Kit を既知として、以下の差分を
読んでいただければと思います。

**仕様そのものの位置づけ**。まず、Spec Kit の spec.md にもっとも近い
のは、本プロセスでいう目的仕様と構造仕様です。目的仕様は受入基準を
含み、構造仕様はアーキテクチャや公開インターフェースを含みます。つまり、
Spec Kit の spec.md に対応する内容は本プロセスにもあります。ただし、それ
が一枚の文書に集約されるのではなく、目的仕様と構造仕様として分かれて
管理されます。

違いが大きいのは、判断記録の扱いです。本プロセスでは、目的仕様・構造
仕様・作業計画の各変更の前に DR や pre-doc 的な検討を置き、検討した案や
棄却理由を履歴として残します。Spec Kit の spec.md や plan.md にも判断の
理由を書く余地はありますが、判断の由来を独立した累積台帳として長期保存
することが中心に置かれているわけではありません。Spec Kit が掲げる
「仕様は静的な文書ではなく、生きた実行可能成果物である」という主張は、
spec.md を更新し、そこから後続成果物を再生成できるという性格を指して
います。本稿はこの点で逆向きで、成果物の最新版だけでなく、そこへ至った
判断の履歴を消さないことに重きを置きます。

**作業計画の位置づけ**。Spec Kit の plan.md と tasks.md に近いのは、
本プロセスでいう作業計画です。ただし対応は一対一ではありません。
マイルストーン計画は plan.md に近く、進捗ノート上の step / タスク列は
tasks.md に近いです。ただし本プロセスでは、詳細な実装手順を長期保存
される成果物としては扱いません。step は実装中に動く作業仮説なので、
進捗ノートに置き、フェーズ終了時には必要な情報だけを判断記録や変更履歴
へ蒸留して、ノート自体は削除します。ここは一般的な意味の「仕様」という
より、仕様から実装へ降りるための計画です。

**反復のモデル**。Spec Kit が示すのは前方への再実行モデルで、spec.md
を更新すれば plan.md と tasks.md を再生成できる、という発想です。本稿
でも目的仕様や構造仕様を見直せば作業計画は組み直します。ただし、判断は
履歴ごと固定し、覆すときは新エントリで上書きします。再生成ではなく
累積に振っている部分がある、という言い方のほうが正確です。どちらが
優れているという話ではなく、最適化の対象が違います。Spec Kit は「変更
時のコストを下げる」ことに、本稿は「過去の判断を後から遡れる」ことに
より強く最適化しています。

**合意の取り方**。Spec Kit のフローには明示的な合意点はありますが、
その重みは均一に描かれています。本稿はこれを **段階的な重みのある
合意** として運用します。事前文書の合意、フェーズ枠への取り込み、
主系列への取り込み、外向けの公開、それぞれに別の判定基準と別の承認
が要ります。とくに「主系列へのマージ」と「公開」を分離するのは本稿
の特徴で、Spec Kit の実装フェーズの中にこの分離はありません。

**仮説の扱い**。Spec Kit においてタスクは仕様と計画から導出される
ものとして描かれ、タスク自体が仮説かどうかは前面に出ません。本稿は
事前文書の段階で **タスク列は仮説、受入基準は制約** とラベルを付け、
事前文書の作業の半分は「もとの計画が本当に受入基準への最短経路だった
か」を問い直すことに使われます。これは、Spec Kit が仕様から計画・タスク
へ降りる流れを強く描くのに対し、本稿ではその下降の手前で「そもそも
この受入基準や作業計画でよいのか」を毎回確認する、という違いです。

**AI と人間の役割分担**。Spec Kit が掲げる「AI が生成し、人間が検証
する」は本稿でも同じですが、本稿のほうがオーナーの判定が深いところ
まで降ります。DR の各案、棄却理由、二軸のリスク、上書きの発火条件
まで、明示的な合意を取る対象に含まれます。これは体制が小さく逐次的
だからこそ成立する密度です。複数チーム・複数エージェントを視野に入れた
枠組みで同じ密度の合意を毎回求めるなら、役割分担や代表制を別に設計
する必要があります。

**道具立て**。Spec Kit はスラッシュコマンドとツールキット (toolkit)
という形で、再現可能なインターフェースを提供します。本稿はそうした
ツールキットを持たず、文書規約と運用ルールだけで成立しています。
これは本稿が Spec Kit の代替を目指しているわけではないことを意味
します。実際、両者は組み合わせて使うことができます。Spec Kit の
スラッシュコマンドで spec.md、plan.md、tasks.md を生成し、spec.md を
目的仕様・構造仕様の初稿、plan.md をマイルストーン計画の初稿、tasks.md
を進捗ノート上の step 候補として扱う。そのうえで、本稿の DR、合意点、
確認項目を上から被せる、という使い方は十分に成立します。

**適用範囲**。Spec Kit は新規開発 (greenfield)、機能追加 (feature
work)、既存システムの近代化 (legacy modernization) の三つを主な適用先
として挙げており、適用範囲が広いです。本稿は適用範囲を意図的に狭く
取り、長寿命・高設計密度・小体制 (次章) に絞っています。元になって
いる実例が UI フレームワークであることも、この絞り込みに影響して
います。エンドユーザー向け機能を素早く追加するより、公開 API、DSL、
ABI、描画モデル、アクセシビリティといった長く残る構造を慎重に決める
比重が高いからです。これも対立ではなく分業に近いです。日々の機能追加は
Spec Kit のフローでよく、プロダクトの骨格を決めるレイヤだけ本稿のような
重めの運用を被せる、という併存も自然です。

要するに、本稿は SDD の系譜から派生しつつ、(1) Spec Kit の spec に
相当する目的仕様・構造仕様を複数文書に分ける、(2) plan/tasks に相当
する作業計画を、マイルストーン計画と進捗ノート上の step に分けて扱う、
(3) DR によって設計判断の遡及可能性を重視する、(4) 合意を段階化する、
(5) 目的仕様・構造仕様・作業
計画を節目ごとに問い直す、という点で Spec Kit と立場が異なります。
Spec Kit を知っている読者には、**「Spec Kit を否定するもの」ではなく
「Spec Kit の外側に被せる運用規律」** として読んでいただけると、
本稿の位置づけが正確に伝わると思います。

**この章のまとめ**: 本稿は SDD の系譜に属しつつ、Spec Kit の spec に
相当する内容を目的仕様・構造仕様に分け、plan/tasks に相当する内容を
マイルストーン計画と進捗ノート上の step に分けて扱います。さらに、その上流に DR を置いて
判断記録を累積し、合意を段階化し、目的仕様・構造仕様・作業計画を節目
ごとに問い直す点で Spec Kit と立場が異なります。代替ではなく、外側に
被せて使うことが可能な運用規律として読むのが正確です。

## 12. このやり方が向いていないとき

ここまで好意的に書いてきましたが、批判的に検討する章を一つ置きます。
本プロセスは銀の弾丸ではなく、適用範囲があります。

**短命なものには明らかに重いです**。数日で書き捨てるスクリプト、
プロトタイプ、社内の使い捨てツール程度のものに事前文書とレビューを
通すのは、得るもの (将来の保守性) と払うもの (即時の進行速度) の
バランスが完全に崩れています。文書を書くべきかどうかの判断軸は「これ
は半年後に誰かが触る可能性があるか?」あたりで切るのが現実的でしょう。
こうした短命なものは、Spec Kit の軽い適用 (spec.md と tasks.md だけ
で回す) のほうが向いています。

**チーム規模が大きくなると別物になります**。本プロセスはオーナー一人
と AI 協働者一体という体制を前提に組まれています (第 2 章)。レビュ
アーが増えると、「全員の合意を毎回取る」のは事実上不可能で、何らか
の代表制 (レビュー担当のローテーション、領域ごとのオーナー分割) を
導入する必要が出てきます。そのとき「合意の単位」をどう再定義するか
が、このプロセスを大きいチームに持っていくときの最初の調整点になり
ます。

**並列エージェントを導入すると合意モデルが崩れます**。本稿は逐次進行
を前提にしているので、複数の AI 協働者を並行して走らせる場合、合意点
とブランチ運用の両方を再設計する必要があります。これは第 2 章で触れた
とおり本稿の射程外で、解決策は別に考える必要があります。

**設計密度が低い領域では文書負担が逆効果**になりえます。たとえばすで
に確立された枠組みの上の薄いアプリケーション開発、あるいは多くがコピペ
で成立する管理画面の量産では、判断らしい判断がほとんど発生しません。
にもかかわらず DR の様式で文書を書こうとすると、中身のない雛形が量産
され、文書全体の信頼性をかえって下げてしまいます。

**心理的な負荷も小さくありません**。事前文書の段階で「自分の最初の
見立てが本当に最短経路だったか」を毎回問い直すのは、慣れないうちは
かなり疲れる作業です。さらに、文書を直すことに対する抵抗感 (一度書い
たものを変えたくない、という感情) を意識的に押さえないと、せっかく
の仮説検証ループが空回りしはじめます。

**情報を複数箇所に重複させない、という規律は地味に難しいです**。同じ
事実が DR にも計画書にも進捗ノートにも書きたくなる場面は常にあり
ます。これを毎回「正本はどこか?」と立ち止まって判断するのは、軽い
認知的コストではありますが恒常的に発生します。

これらを踏まえると、本プロセスが効くのは概ね次のような領域です。

- プロダクトを中長期で継続的に育てる前提が置かれている
- 設計判断が後々まで影響を残す層 (アーキテクチャ、公開インターフェース、
  データ構造、プロトコル)
- 開発者向け基盤、ライブラリ、フレームワークのように、利用者が公開面に
  長期依存する
- 体制が小さく、意思決定者が明確
- 協働者が AI である、または交代しうる人間である

逆にこのどれも当てはまらないなら、もっと軽い運用 (Spec Kit のフロー
だけ、あるいはそれもなしの口頭合意) を選んだほうがよいです。

**この章のまとめ**: 本プロセスは長寿命・高設計密度・小体制・逐次進行
の組み合わせで本領を発揮します。短命なもの、設計判断の少ない領域、
大きなチーム、並列エージェントを伴う運用では、そのまま適用すると負担
が成果を上回る可能性が高いです。

## 13. おわりに

適応的・反復的に仮説検証を回しつつ、その経過と合意を文書として積み
重ねる、という一文に集約される話を、いくつかの角度から書き出しまし
た。原則として残しておきたいものをもう一度並べると、

- 設計判断をコードより先に文書として固定する
- 着手前のタスク列は仮説、合意済みの判断は制約として扱う
- 文書カテゴリの役割を一つに絞り、情報の正本を一箇所に置く
- 本プロセスの「仕様」は、目的仕様と構造仕様を中心に置き、作業計画
  (マイルストーン計画と進捗ノート上の step) と判断記録を別種の文書
  として周囲に置く
- マージは段階的な合意点として、段ごとに基準を変える
- 振り返りはマージ前の確認項目として運用する
- DR は検討した案の網羅と履歴の不可逆性を保つ

これらは互いに独立に見えますが、実際には「合意を、文書として、明示
的に取り続ける」という一本の軸に乗っています。どれか一つだけを抜き
出して持ち帰っても効きますが、いちばん効くのは全体を回し続けたとき
です。

本稿を貫く前提を最後にもう一度書いておきます。本稿で記述したのは、
**人間のオーナー一人と AI 協働者一体という体制で、中長期で育てる
前提を置いた単一プロダクトを逐次的に進めている** という、特殊な配置
における運用です。運用の実歴はまだ短く、本稿はその範囲内で固まった
ルールを書き出した、現時点での到達点にすぎません。体制が変わればモデル
は作り直しになりますし、寿命が短ければ重すぎます。v1 接近時の RFC
移行など、ここからさらに上の層が積まれていく余地もまだ残っています。
SDD の系譜としては Spec Kit の外側に被せる運用規律という位置づけ
になり、Spec Kit そのものの代替にはなっていません。

本稿はあくまで雛形で、運用してみるとすぐに自分のプロダクト固有の調整
箇所が見えてくると思います。受入基準の粒度、振り返りの項目、ファスト
トラックの判定軸あたりは、最初の数フェーズで揺れることをあらかじめ織り
込んでおくとよいです。そして揺れたときには、迷わず文書のほうを直し
ましょう。

## 補遺: kawasima 氏「仮説階層モデル」との対応

本稿を書き終えた後で、kawasima 氏の Scrapbox にある
[仮説階層モデル](https://scrapbox.io/kawasima/%E4%BB%AE%E8%AA%AC%E9%9A%8E%E5%B1%A4%E3%83%A2%E3%83%87%E3%83%AB)
を読みました。本稿とは独立に書かれた文書ですが、結果として似たこと
を考えている部分があったので、おまけとして対応関係を書き留めておき
ます。詳しく論じるものではなく、関心のある読者への手がかりという程度
のものです。

kawasima 氏のモデルは、仕様を「正解を先に固める文書」ではなく「仮説
を構造化し、どのエビデンスで採択・棄却するかを明示する文書」として
再定義することを提案しています。階層は **価値仮説・行動仮説・ドメイン
仮説・相互作用仮説・実装仮説** の五つで、それぞれ採択基準とエビデンス
の種類 (リリース後の指標、ユーザー観察、業務ルールとの整合、ユーザビリ
ティテスト、ベンチマーク) が異なります。

本稿との対応を緩く取ると、四点ほどあります。

- **仕様を仮説として扱う基本姿勢が共通しています**。本稿の「タスク列
  は仮説、合意済みの判断は制約」(第 4 章) と、kawasima 氏の「仕様を
  仮説として書く」は同じ方向を向いています。
- **層を分ける発想も共通しますが、切り口が違います**。本稿は目的仕様・
  構造仕様・作業計画・判断記録を、更新規律と時間スケールの違いで分けます
  (第 6 章)。これに対し、kawasima 氏は採択に必要なエビデンスの種類で
  五層に切ります。
- **低い粒度の判断が勝手に高い粒度の合意を規定するのを防ぐ** という関心も共通
  します。本稿の動機の一本 (第 1 章・第 6 章) と、kawasima 氏の「上位
  の不確実性を残したまま下位を実装すると手戻りが膨らむ」は呼応します。
- **素朴な仕様駆動開発への批判的距離**。kawasima 氏は Kent Beck や
  Marmelab の批判を引きつつ「仕様を判断基準として再定義すべき」と論
  じています。本稿の Spec Kit 比較 (第 11 章) と立場が通じます。

違いは重心の置き場所にあります。kawasima 氏の例は、注文履歴や再注文
のようなアプリケーション機能を題材にしており、**製品の方向決定** (何
を作るか、作る価値があるか) に重心があります。そのため、上位仮説の
検証手段に紙幅を割いています。本稿は **設計判断と合意プロセスの運用**
に重心があり、合意点・振り返り・判断記録の作法に紙幅を割いています。
この違いには、本稿の元になった対象が開発者向け UI フレームワークで
あることも効いています。業務アプリケーションなら、価値仮説・行動仮説・
ドメイン仮説の検証が前面に出やすいでしょう。一方で UI フレームワーク
では、開発者が長期に依存する公開インターフェースや拡張余地、サンプル
アプリでの実証、性能・アクセシビリティといった構造側の判断が重くなります。両者は
対立しているわけではなく、扱う対象の性質と重心が違うと言ったほうが
正確で、重ねて読むと相互補完的に見えるかもしれません。

独立に書かれた文書が結果として似た構図を持つのは、おそらく LLM/AI
協働を前提とした開発において「仕様を凍結された契約として扱うこと」が
いよいよ持たない、という共通の状況認識があるからでしょう。
